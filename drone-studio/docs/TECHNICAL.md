# Lucidity Drone Studio — technical architecture

**v0.4 · September 27, 2026 · Immersive viewer, expert foundation, and proposed extensions**

## Architecture decision

The authoring primitive is an identifiable, animatable light in 3D space. Parametric formations seed a scene; they do not constrain its final geometry. Explicit point edits and animation channels can replace generated values. UI gestures, source edits, and agents mutate one document through atomic revision-bound commands.

The viewport uses **Three.js/WebGL**, React for editor chrome, and Web Audio for time. Three.js provides spatial transform controls with translate, rotate, and scale modes; the application supplies selection, coordinate conversion, shared animation evaluation, and history. [Three.js TransformControls](https://threejs.org/docs/pages/TransformControls.html).

Blender is a potential asset and offline-render integration. It is not embedded in this build. Keeping a renderer-independent document/evaluator makes a future bridge possible without making Blender’s UI the studio’s architecture. The current output is creative design data; a mission compiler remains a separate, future subsystem.

```text
Viewport gestures ─┐
Inspector + keys ──┼── atomic command batch ── Project v1 + explicit drone animation
Scene JSON ────────┤           ▲                            │
Agent CLI ─────────┘       undo / redo                      ▼
                                                    ShowEvaluator
                                            ┌──────────────┼──────────────┐
                                            ▼              ▼              ▼
                                      GPU preview    sampled review   JSON / CSV
                                            ▲
                                      Web Audio clock
```

## Document contract

Project fields include name, revision, fleet size, manual BPM, ordered scenes, and proposed physical limits. Schema checks protect data integrity, finite values, unique identities, and resource bounds. Physical review is separate: artistic coordinates can be negative or exceed stage limits without being rejected as an edit.

```ts
type Cue = {
  id: string;
  name: string;
  transitionEasing?: 'smooth' | 'linear' | 'ease-in' | 'ease-out';
  shape: 'orbit' | 'sphere' | 'helix' | 'heart' | 'wave' | 'bloom' | 'grid' | 'custom';
  palette: 'aurora' | 'moonlight' | 'ember' | 'rose' | 'ocean';
  duration: number; // 1/30 second through show budget
  transition: number; // 0..duration; zero means a creative cut
  scale: number; // positive seed-generator scale
  altitude: number; // seed-generator center; local ENU z
  droneEdits?: Record<
    string,
    {
      position?: [number, number, number]; // arbitrary absolute ENU position
      color?: string; // #RRGGBB
      brightness?: number; // 0..1
      flash?: { hz: number; duty: number; phase: number };
      keyframes?: Array<{
        time: number; // scene-local seconds
        easing?: 'linear' | 'smooth' | 'hold';
        position?: [number, number, number];
        color?: string;
        brightness?: number;
        flash?: { hz: number; duty: number; phase: number };
      }>;
    }
  >;
  metadata?: Record<string, unknown>;
};
```

Coordinates are **local ENU meters: x east, y north, z up**. The visual transform is `(x, z, -y)`. No geographical origin is implied. Drone IDs are one-based stable point indices. Project count determines active IDs; entries above that count remain dormant and reappear when the count grows. Unedited parametric seed points regenerate with the new count, so they may move. Explicit authored positions retain their identity and values.

`custom` provides a neutral field for any explicitly authored geometry; missing explicit positions use the seed grid. The procedural example writes all 800 positions rather than relying on a new shape enum. `metadata` preserves generator/source annotations. Source parsing still rejects malformed channel values; flexibility does not mean accepting corrupt data.

Current engineering bounds: 100,000 IDs, 512 scenes, total duration 1,800 s, up to 2,048 keys per drone per scene, and 32 MB JSON import. These are resource limits, not a claim that every combination is interactive. The audio importer separately caps files at 80 MB and 30 minutes.

## Evaluation semantics

`src/core/animation.ts` contains `ShowEvaluator` and the shared channel evaluator.

1. Generate the scene’s base position/RGB buffers, then apply explicit static point positions.
2. For each edited drone, sample each channel independently at the scene-local time. Omitted channels inherit base values. Position, color, and brightness interpolate between their own keys. Flash parameters use a held value.
3. The first and last key in a channel extend to scene boundaries. The left key’s easing controls the following segment. `smooth` uses the quintic `6u⁵ − 15u⁴ + 10u³`; `hold` changes at the next key.
4. Apply brightness and flash gating to RGB. Flash is on when `fract(showTime × hz + phase) < duty`; frequency zero is steady. Phase is in cycles. Flash phase uses the global show clock.
5. Blend the previous scene’s final animated pose/light state toward the current animated target through the incoming transition. Zero transition cuts directly. Scene zero starts already formed.
6. Apply the demo beat pulse `0.9 + 0.1 cos(2π × BPM × showTime / 60)`.

Key times move with their scene. A scene trim does not scale or delete its keys; later keys remain dormant. Increasing the duration exposes them again. Animated target motion during an incoming blend is not the same as a static minimum-jerk trajectory, so the older analytic bounds cannot certify it.

The evaluator caches at most three prepared scenes. It is shared by GPU attribute generation, picking, numeric properties, sampled review, and CSV. No independent animation approximation is used for export. CSV sampling is still lossy in time: fast flashes and short motion events require the full keyframe artifact or a future higher-rate compiler.

## Viewport and editor

`Stage.tsx` maintains four packed attributes: source/destination positions and colors. Shader interpolation draws every active drone as a point; no per-drone React elements or Three.js meshes are created. At 100k the raw four attribute buffers total about 4.58 MiB, excluding CPU copies, cached scenes, selections, framebuffer targets, and overhead.

Static scenes upload on scene/project changes. Animated channels update the prepared attributes when show time changes. Buffer allocations are reused when the fleet/selection size is stable. This is a practical baseline, not a benchmarked six-figure animation engine; channel preparation and uploads need profiling before GPU compute or worker optimizations are chosen.

**Viewer 360°** is the default camera mode. It begins at ENU East 0 / North 0 / Up 1.7 m, within the authored space, with a reference stage centered 70 m north. It uses a fixed-position perspective camera: drag or focused-canvas arrow keys change yaw/pitch, while the wheel adjusts field of view. Home faces the stage; stage/left/right/behind/sky controls provide direction presets. A heading indicator and compass show orientation relative to the stage. Horizontal look wraps through 360°; pitch is bounded to −20°..89° to avoid a vertical camera singularity.

The audience controls provide Center/Rear/Left/Right positions, custom East/North coordinates within ±500 m, eye height 0.5–5 m, and vertical field of view 45°–100°. A plan supports dragging and keyboard positioning of viewer and reference stage independently, each within ±500 m East/North. Venue heading is its front-facing compass direction, 0°–359°, defaulting to 180° south. [viewer.ts](../src/core/viewer.ts) contains finite-value validation, pose normalization, ENU/world direction conversion, and stage-bearing math. The camera world position is `(east, eyeHeight, -north)`; the reference stage position is `(venue.east, 0, -venue.north)`. Its geometry faces local +Z, so world-Y rotation is `(180 − venue.heading)` degrees. Looking toward the stage uses the bearing to its center, independently of the stage's front heading. No transform is applied to drone buffers.

[viewerVenue.ts](../src/components/viewerVenue.ts) creates the ground, stage architecture, distance marks, and abstract audience with local Three.js geometry and lighting. It is visible only in Viewer 360°. Its reference stage moves and rotates independently of both the authored show and the audience ground. Active viewing preferences are outside Project; explicit local bookmarks persist selected camera and reference-stage configurations.

A saved `ViewerSnapshot` contains `pose: { east, north, eyeHeight, yaw, pitch, fov }` and `venue: { east, north, heading }`. Capture uses the current runtime camera pose, including unrounded yaw/pitch and vertical FOV, rather than the throttled orientation display or its derived horizontal FOV. Recall restores the exact saved pose and venue rather than recomputing a default stage-facing direction. It leaves show time and appearance controls unchanged and preserves the Design camera.

Bookmarks use a separate local-storage key, `lucidity.viewer.bookmarks.v1:<encoded projectId>`, with a strict version-1 envelope capped at 64 KB, up to 12 entries, and names of at most 48 characters. Save, recall, and removal are explicit; the active viewpoint is neither autosaved nor automatically recalled after reload. Unknown versions, malformed content, and storage errors are reported without overwriting the existing stored value. These local preferences do not alter project identity, revision history, choreography, JSON/CSV exports, or camera tracks.

`camera-audition.ts` defines owned, strict camera-move plans with canonical endpoint snapshots, a 1–30-second duration, and linear or cubic smoothstep easing. Both venue snapshots must be identical; Stage additionally requires that layout to match the current reference stage. Sampling returns exact owned endpoints, linearly interpolates position/height/pitch/FOV with the eased amount, and uses the shortest yaw arc with a positive 180-degree tie. The finite clock uses elapsed seconds and millisecond anchors, clamps seeks, ignores backward clock deltas, and holds the exact endpoint without restarting.

Stage advances camera audition in its existing RAF, independently of show time, and publishes control state at most every 100 ms while moving. One internal snapshot installer atomically updates yaw/pitch, viewer/venue refs, and synchronization baselines so translated poses do not get re-aimed at the stage. Snapshot reads settle between RAFs; rebasing never moves the timestamp backward when an older RAF timestamp follows a synchronous read. Camera capture pauses the camera first, then settles the show clock under the existing exact-frame capture contract. Same-project A/B changes retain the path; project-ID changes invalidate it before another sample.

`CameraAudition` separates uncommitted form fields from the prepared plan and keeps its controls within a scrollable Stage panel. Explicit successful preparation reveals/focuses Play; ordinary clock updates never scroll it. Closing the panel or opening viewing settings pauses and publishes the current pose. Direct look input, lens/position/venue edits, direction controls, and bookmark/evidence recall clear the move before applying manual changes. Design, WebGL context loss, and Stage unmount also clear it. The existing renderer owns the only animation loop. No Project mutation, local-storage write, authored camera track, provider tool, or export field is added.

`camera-move-inspection.ts` adds a shared read-only report over a captured `CameraAuditionPlan`, aspect, endpoint names, show start/end, and 2–12 samples. Camera elapsed time spans zero to duration, while show time maps linearly from start to end (equal endpoints hold the show). Both exact endpoints are retained. Each sampled pose comes from the same audition helper and each fleet count from `inspectAudienceFrame`, including blended motion and light modulation. All point/key budgets are preflighted before evaluation: two million point inspections, twenty million aggregate weighted key operations, and the existing per-frame budget. Project/request/snapshots are owned before the first yield; cancellation is checked between samples; no partial report is returned. Summary extrema use earliest ties and mean is the arithmetic sample mean.

`CameraMoveInspection` runs this in a dedicated terminable worker with generation and project guards. Failed/cancelled reruns preserve the previous report, and older project revisions cannot be inspected. Stage's prepared-path getter clones plan metadata and captures the current render aspect without publishing React state or changing a clock; the explicit Analyze action pauses before opening the modal. Inspect explicitly recalls a report snapshot and seeks the Stage's transport; normal recall clears the camera move. Captured aspect remains report metadata, so resizing can change the current viewport's projection. No camera track or authored Project operation is produced.

The thirteenth harness tool, `inspect_camera_move`, resolves captured current/saved IDs and invokes the same Promise against the private draft with its AbortSignal. It preserves completed review. Its compact trace retains exact endpoint poses/venue, projection, camera/show time mapping with one `inFrameLights` count per row, summary, limitations, and harness-generated revision/operation-count provenance while omitting duplicate full per-sample totals. The provider receives the bounded full report; default scripted rehearsal remains unchanged.

The audience pipeline is a render pass, UnrealBloomPass, and OutputPass with ACES tone mapping. Exposure/glow are display controls and do not alter exported RGB. Point sprites shrink with fleet density; subpixel coverage attenuates their displayed energy to prevent the one-pixel rasterization floor from washing out distant dense formations. This is a legibility treatment, not a calibrated photometric simulation. Design mode retains OrbitControls, orbit/front/top cameras, the 10 m grid, fit-to-formation, and spatial gizmos; bloom and reference venue are hidden there. Switching back restores the saved Design camera. The design envelope uses the project radius. Design camera fitting animates unless reduced motion is requested. Idle, unchanged frames skip rendering.

This is a desktop perspective viewer, with no VR/headset integration, spatial audio, portable venue assets, camera-track export, or video renderer. Local saved views preserve viewing preferences only; these display changes do not modify show geometry, animation, revision history, or handoff artifacts.

The toolbar's **360° study** opens `ImmersiveStudy.tsx` in a separate modal. It fetches and parses `public/examples/immersive-study.lucid.json` into component-local state, supplies a read-only `Stage`, and owns an independent silent playback clock/scrubber. Opening pauses the main transport; it does not invoke the existing editable-example replacement path or change main project/history/selection. Fetch and animation work are cancelled on unmount. `createImmersiveStudy()` in `src/core/immersive-study.ts`, exported by `scripts/immersive-example.ts`, authors the _All around you_ project: 1,200 stable light IDs, three 16-second scenes, position/color/brightness keys, and a 120 BPM grid without embedded audio. The downloadable design remains `flightReady: false`.

Picking projects the currently interpolated points into screen coordinates. Box selection and Shift toggling produce ID sets. TransformControls acts on a proxy at the selection centroid. Its transform matrix is applied to every selected point. During an incoming blend, the desired visual position is converted back to the corresponding target position. The gizmo is inactive when the target’s blend weight is effectively zero; numerical/source edits remain available. A completed gesture commits one batch, and Escape cancels a transform.

The inspector edits ENU values and light channels. Auto key writes at the local playhead; disabled auto key edits base properties, which existing keyed channels override. Explicit key capture records all channels. Scene source is an editable JSON view with atomic application and revision checking, not a JavaScript execution environment.

The timeline uses one pixel/time scale for rendering and hit testing. Scene movement is a batch of adjacent moves, so one gesture is one revision. Outgoing cuts snap to the global beat grid; Shift bypasses to 30 fps edit precision. This edit/display frame rate does not quantize the audio clock or stored animation times. Keys can be dragged or nudged and reject collisions with an existing timestamp.

Undo/redo retain up to 30 project snapshots in session memory; revisions remain monotonic. A new edit clears redo. Browser reload retains the current project, not history, selection, layout, or audio. Full snapshots are convenient at MVP scale; production needs structural sharing or patches and durable revision storage.

## Agent contract

Commands include project/scene operations plus `edit_drones`, `transform_drones`, `set_keyframe`, `move_keyframe`, `remove_keyframe`, and `reset_drones`. Every batch applies to a clone and validates before publishing a new revision. Invalid or stale edits do not partially apply. [Tool manifest](agent-tools.json).

```json
[
  {
    "type": "edit_drones",
    "cueId": "in-orbit",
    "ids": [1, 2, 3],
    "patch": { "color": "#ff6d43", "flash": { "hz": 2, "duty": 0.4, "phase": 0 } }
  },
  {
    "type": "set_keyframe",
    "cueId": "in-orbit",
    "ids": [1],
    "keyframe": { "time": 20, "position": [12, -4, 80], "easing": "smooth" }
  }
]
```

```bash
npm run --silent agent -- --project show.lucid.json --expected-revision 5 \
  --commands-file operations.json --validate
```

External scripts can compute arbitrary geometry and write operations or a project. `scripts/expert-example.ts` demonstrates explicit point generation and time-varying geometry/colors. The CLI writes results to stdout and leaves input files untouched.

The embedded assistant now uses a provider-neutral bounded loop with a server-only OpenAI Responses adapter. It captures project identity/revision, scene, selection, and playhead; retrieves large data through tools; stages changes on a private copy; reviews them; and returns the original revision plus exact operations. Complete selection paging and a selection operation handle avoid truncating large ID sets. The UI exposes tool activity, authoritative review findings, raw operations, a read-only animated draft viewer, and explicit atomic application. Cancellation invalidates late results. Local NDJSON transport streams tool progress; model responses are currently buffered per turn. Credentials are read only on the server. See [AGENT_HARNESS.md](AGENT_HARNESS.md) for budgets, persistence limits, key setup, and live qualification boundaries.

Optional audience context captures the main viewer's exact current snapshot/aspect and up to 12 saved snapshots at submission. `inspect_show` exposes the available view IDs. `inspect_viewpoint` accepts show-global time, an empty view ID for the captured current view or a saved ID, and a representative-row limit of 1–32. `audience-inspection.ts` uses `ShowEvaluator` to count the entire active fleet in stage-relative quadrants, overhead elevation ≥70°, and a perspective frustum with 0.1–5,000 m camera depth. Geometry counts are independent of positive evaluated RGB; the report also provides their intersection and evenly spaced representative IDs. All saved views use the captured current viewport aspect. The report reflects the current private draft while the captured camera context stays fixed.

Inspection is read-only and does not invalidate review. It includes actual incoming blends, keyed motion, brightness, flashing, and beat modulation, but no screenshots, rendered-pixel measurement, occlusion, venue obstruction, photometric visibility, or flight certification. Frame inspection and `sample_frame` reject relevant current/previous-cue workloads above five million estimated key operations before constructing the evaluator; the estimate weights active key count by channel scans and sorting.

`audience-comparison.ts` shares this inspection primitive between the studio and the twelfth agent tool, `compare_viewpoints`. Requests contain a strict show interval (`0 <= start < end <= duration`), 2–12 equally spaced samples including exact endpoints, and 1–4 unique captured view IDs/snapshots/aspects. Preflight bounds fleet × samples × views at two million point inspections and aggregate weighted key work at twenty million, in addition to the existing five-million per-frame bound. It clones the project/views before the first await, yields an event-loop turn between inspections, and rejects an aborted run without publishing a partial report. Results include project identity/revision, explicit times, captured view metadata, full-fleet totals per moment, and min/max/arithmetic-mean `inFrustumLightsOn` summaries; ties use the earliest sampled time.

`AudienceComparison.tsx` captures fresh available viewpoints when Run is pressed and dispatches one request to a dedicated module worker. Cancel, unmount, or project identity/revision changes terminate that worker; generation and identity guards discard late messages. Failures preserve previous reports, and stale reports disable Inspect. Main Stage, independent study, and draft-preview transports each supply their own seek callback; Inspect recalls the exact captured snapshot before seeking and closing the report. This explicit action does not author camera keys or change show data. Dialog portals support nested previews and topmost keyboard dismissal/focus trapping. The agent awaits the same core Promise with its AbortSignal, keeps completed reviews valid, and records compact snapshot/aspect/time/summary trace evidence without copying all sample rows into the trace.

`createAudienceFrameClassifier` in `audience-inspection.ts` centralizes the exact per-drone blended positions/RGB, camera-frustum inclusion, stage-relative quadrant, overhead, and light-state calculation. Existing inspection totals/representatives and the new `audience-selection.ts` both use it. Selection owns its project, canonical snapshot/aspect/time, region/light criteria, and optional stable-ID scope before any observer or yield. Scope omitted means all active drones; explicit `[]` means none. Valid IDs 1–100,000 are deduplicated/sorted, dormant IDs remain in the captured request but are excluded from considered/matched IDs. The existing whole-frame key-work budget runs before evaluation even for a narrow scope. An empty active scope skips the evaluator. Selection yields before synchronous evaluation and every 1,024 classified IDs, checks cancellation including after the final chunk, and returns only a complete report.

`AudienceSelection.tsx` uses a dedicated module worker with generations and project/revision guards, retaining an earlier complete result on failures or cancellation and disabling stale commits. Run captures current viewing context, show time, and scope; form changes do not relabel a historical result. Only explicit Replace/Add passes the complete result to the main Stage's existing `onPick`. Stage translates Add into a Set union and passes `additive=false`, because the existing pointer-selection additive flag means toggle/XOR. This avoids duplicate toggling and quadratic membership checks at large counts. The dialog is unavailable in read-only study/proposal Stages. Viewer displays the selected count; spatial rings and gizmos remain in Design.

The optional **Preview matches** action validates and deeply owns the complete report through `audience-highlight.ts`, including canonical view, query criteria, sorted active IDs, optional dormant scope IDs, counts, and cue/time/blend metadata. One frozen target is retained in Stage session state. An O(1) project/revision/fleet guard prevents stale rendering and selection before effect cleanup; read-only transitions also clear it. Preview leaves selection, camera, and show time untouched while pausing playback. The card exposes historical membership and current position times, explicit selection union/replacement, and optional camera/time recall. A keyboard boundary preserves native button activation without triggering editor playback shortcuts.

Audience rings use a separate Points scene rendered after the main composer, outside bloom and exposure, with depth disabled to reveal matched dark/occluded locations. A reused Float32 buffer holds exactly the selected IDs' current blended positions in Three.js coordinates (East, Up, -North). The shared writer preflights all inputs, finite coordinates, capacity, and buffer overlap before writing; it leaves source arrays and unused output capacity unchanged. At 100,000 matches this adds 1.2 MB for the CPU position array plus its GPU attribute. Hidden/Design/stale targets perform no position writes or uploads; target/frame changes refresh visible geometry. Capture renders skip the overlay; read-only previews cannot enable an artist query target. Context loss stops rendering, and unmount disposes overlay resources. No authored RGB or motion data changes, no model image input, and no large-fleet frame-rate qualification follow from these markers.

`inspect_audience_selection` pages that same report with at most 128 sorted IDs per call, complete counts, and continuation metadata. It evaluates the current draft against an owned run viewpoint, optionally intersecting the original captured selection with active IDs, and never mutates that selection or invalidates completed review. A nonempty result includes an opaque `targetId` for the complete matching set; empty results return null. Full scope/match arrays are not copied into a provider page or trace.

The run retains at most eight targets and 200,000 total matching IDs, evicting oldest targets first. Each owns its exact query context, IDs, project identity/revision, and staged-operation count. Registration checks cancellation and the original draft identity after asynchronous classification. `stage_audience_operation` accepts one existing per-drone command with explicit scene ID and no supplied drone IDs, injects the complete target IDs, and uses the existing atomic replay and expansion limits. Successful staging invalidates every target; failed staging leaves targets available for repair. The store uses copy-on-write updates so tool-result budget failures and cancellation restore it with the existing harness checkpoint. Handles stay inside one run and are neither persisted nor recovered; final proposals contain ordinary explicit-ID operations. This adds no implicit live selection change or camera review link.

Follow-up requests carry exact unapplied operations, bound to the original project ID/revision. The harness restages them with the same command and expansion limits, supplies the resulting draft as model context, and requires a fresh review. Final operations include both the retained and new edits. Failed/stopped refinements retain the preceding proposal in the UI; manual edits mark it stale. Direct drone inspection avoids scanning a complete authored scene.

`draft-preview.ts` captures independently owned baseline/draft documents after project ID/revision validation, privately applies the exact proposal, and normalizes an optional audience snapshot. Its shared-clock helper spans the greater total duration and clamps each displayed document's sample time independently, marking held end frames only after that document's endpoint. `AgentDraftPreview.tsx` uses a single persistent read-only `Stage` for Before/Draft switching, preserving camera, appearance, and viewport aspect while changing evaluator input. The optional `initialViewerSnapshot` is captured once per Stage mount and installed before its first render; it is not reapplied on project switches. The preview owns its playback clock, pauses main music, and never commits. Stale proposals close the preview under the existing revision guard.

`AgentDraftPreview` expands through session-local layout state and a class on its existing DOM root. Direct-child modal selectors resize only the owning dialog; the single Stage is neither portaled nor conditionally remounted. A read-only `comparisonExpansion` prop delegates Stage’s corner action to the same layout toggle, while other Stage uses keep their native fullscreen path. The existing ResizeObserver updates projection and raster dimensions without resetting the camera. Review controls stay mounted inside a collapsible scroll region; their inputs and audition state survive closing the tray. Expansion consumes Escape only for the topmost owning dialog, including its heading, and returns focus to the layout toggle. Nested modal Escape and focus trapping remain with Modal.

`draft-preview-targets.ts` derives a frozen complete union of explicit IDs after successful proposal replay. It parses the six granular command families (base edits, transforms, setting/removing/moving keys, resets), counts other command records without inferring targets, and retains no-op and later-removed-scene targets as command intent. The 128-command proposal limit and stable-ID range 1–100,000 bound this work. Independently owned Before/Draft records filter the same union against their respective active fleet and bind identity/revision/count. No source operation or selection arrays are retained, and no work is repeated on animation ticks.

`AgentDraftPreview` defaults target markers off and scopes the toggle to the owned comparison. It supplies a distinct version-bound minimal target to Stage; only read-only Stages accept this proposal display prop, while editable Stages keep their own audience-query path. The same packed post-composer renderer follows current positions, switches draw ranges across fleet changes, and excludes inactive IDs. The in-Stage card stays available in the expanded comparison, reports complete versus active/inactive counts and unmarked broad operations, and exposes no selection/authoring action. Design suspends it. Capture copies the unmarked bitmap and dirties one subsequent frame to restore paused display rings while encoding proceeds. Targets describe the entire proposal across scenes, not visual differences at the current clock or all effects of broad scene/show operations.

`draft-preview-navigation.ts` derives editing landmarks from those owned documents, reusing authored impact and stable scene IDs. Its optional impact `sceneLimit` is 1,024 (the maximum union of two 512-scene documents); other consumers retain the default 12. The preview memoizes this work outside its animation loop. Each side owns its scene start/duration and global/local landmark times; added or removed scenes have a null opposite side. Downstream start shifts alone do not count as authored edits. Current scene readouts independently use `frameAt` at each clamped document time, so an exact internal boundary belongs to the incoming scene and the final endpoint remains the last scene. Edited-key landmarks are bounded first/last timestamps on active drones within that side's scene, excluding nonfinal end keys and values that round onto the next scene boundary. Landmarks do not evaluate geometry or claim the onset of a visible difference; interpolation may propagate a changed key earlier. Whole-show fleet, tempo, limits, and name changes remain explicit even without changed scene records. `frameAt` checks the global transition endpoint before subtracting the scene start, avoiding a fractional endpoint such as 30.4 seconds being treated as incomplete through cancellation error.

`draft-preview-playback.ts` provides deterministic validation and elapsed-time sampling for private audition playback. An optional loop range is finite, positive, within the longer document's duration, and interpreted as `[start, end)`. Without it, playback reaches the exact full-show endpoint and stops; with it, modulo sampling preserves overshoot across delayed frames and multiple wraps. The supported preview rates are 0.25, 0.5, 1, 1.5, and 2. Rate affects elapsed wall time only; the existing per-document timing helper still independently clamps shorter versions. A paused seek can leave an active range, while the next start normalizes back to its In point. `draft-preview-audition.ts` constructs owned preset ranges that enclose a selected stable scene ID across the two documents; shifted or reordered scenes can produce a range containing intervening scenes. Incoming-blend presets omit cuts and first scenes, whose transition property is inactive. None of these helpers generates formations or scans authored keys per playback frame.

`useDraftPreviewPlayback.ts` owns the preview's RAF lifecycle and settles its old clock synchronously before a speed change or pause. Commands cancel the pending frame and increment a generation so an earlier callback cannot overwrite a seek, range change, or unmounted preview. Rate changes rebase at the settled time and continue only if that old clock has not ended. The selected Before/Draft version is absent from the transport lifecycle. Editable In/Out strings remain separate from the committed validated range; invalid submissions cannot replace it. Marking a bound uses the exact time returned by pause, rather than the preceding React-rendered frame.

`review-moments.ts` derives up to 12 owned navigation records from the completed run's full events and the exact documents produced by `createDraftPreview`. Successful audience results are stamped by the harness with project/base/evaluated revision and staged-operation count; private revision alone cannot distinguish intermediate batches because every replay produces base revision plus one. Zero operations identifies the original document and the final proposal's exact count identifies the completed draft. Unique matching tool-start/result pairs, finite in-document times, canonical captured snapshots/aspects, bounded counts, and comparison extrema at actual sample times are required. Intermediate, malformed, legacy, and recovered traces without provenance yield no links. Recent equivalent version/time/pose/aspect moments are deduplicated before the cap, retaining representation from both documents when available. The helper reads at most 256 events and never parses model prose into actions.

Camera-move records additionally require the completed result's optional owned `viewer` context. The harness clones this validated run capture when returning success; failure/cancellation and restored checkpoints do not invent it. Endpoint IDs, names, canonical poses, fixed venue, and aspect must match this capture exactly. The validator checks every camera/show mapping against the core sampling formula and recomputes minimum, maximum, earliest-tie indices, and mean from the bounded lit counts. It reconstructs the selected extrema poses with `sampleCameraAudition` and records optional camera metadata separately from the moment's show-global `time`. Held-show samples with different poses remain distinct. Missing legacy fields omit camera links without affecting valid sibling evidence. These consistency checks are not cryptographic proof or re-evaluation of the entire show.

`AgentReviewMoments` labels camera elapsed/duration, sample number, easing, show time, version, and source event. The existing Open handler pauses, selects the version, seeks show time, recalls the sampled pose, and offers the captured aspect toggle; it does not play an inferred trajectory. `/test-fixtures/camera-review.html` is a development-only browser entry that creates a synthetic completed camera evaluation and mounts this actual preview without the saved-project editor. The production Vite entry does not include this page.

The preview installs a narrow `Stage.recallViewerRef` command for explicit review-moment actions. Recall uses the existing camera API and switches Design to audience mode without replacing the renderer or changing exposure/glow. Opening a moment pauses, selects its document, seeks its show time, recalls the captured pose/venue, and supplies its aspect as a `Stage.audienceFrameAspect` candidate; audition settings remain. No screenshots are provided to the agent, and these numerical counts do not represent rendered pixels or occlusion.

Stage owns an off-by-default **Captured frame** toggle. `viewer-frame.ts` computes a centered contain rectangle in fractional CSS pixels while retaining the exact requested projection aspect. Eligible aspects satisfy the captured context boundary plus a finite Float32 projection coefficient at the narrowest supported audience lens (45°). This omits numerically unrenderable historical candidates without changing the agent transport schema. Missing/unsupported aspect uses the full viewport; empty or unrepresentable viewport geometry returns null.

The full-size canvas host retains the surrounding controls; only the actual canvas is positioned and sized to the frame. Renderer and composer share its dimensions, with a minimum one-pixel logical allocation for subpixel frames and exact fractional CSS size. The camera uses the captured aspect rather than a rounded buffer ratio. Sprite height and audience drag sensitivity use the fitted frame. ResizeObserver handles host changes; RAF reconciles mode/aspect changes without reallocating unchanged targets; context capture synchronously resolves pending frame changes. Unavailable frames hide the canvas and suppress rendering/capture until resize recovers. Design restores full-host geometry and aspect, retaining the toggle for Viewer. A/B, time, appearance, and the mounted renderer remain independent of framing; fullscreen exposes the same toggle.

Private previews supply Stage with a Before/Draft identity, shared clock, and synchronous pause command for local PNG capture. A capture intent owns the camera, exact aspect, framing mode, and appearance, and retains the exact owned Project reference. `review-frame-request.ts` permits the original pre-pause time pair to wait for React publication, then requires the settled shared/sample pair with paused playback. A changed document, side, seek, camera/venue, framing, or appearance rejects a queued capture. Each Stage permits one job, with a ten-second whole-job timeout and explicit cancellation/context-loss/unmount settlement.

The matching RAF forces `EffectComposer.render()` even when the scene was already clean. It builds owned metadata and calls `canvas.toBlob` synchronously before leaving that callback. The browser then serializes its copied bitmap; later view changes do not rewrite the historical still. This follows the [WebGL drawing-buffer rules](https://registry.khronos.org/webgl/specs/latest/1.0/#2.2) and [HTML toBlob algorithm](https://html.spec.whatwg.org/multipage/canvas.html#dom-canvas-toblob), without enabling `preserveDrawingBuffer`. Postprocessing is included; DOM overlays and frame margins are outside the PNG.

`frame-capture.ts` validates bounded owned metadata (schema version 1, project/revision, side, shared/sample/scene time, held status, fleet, pose/venue, exact projection aspect, framing, raster size, glow/exposure, UTC timestamp) without traversing authored drone/key payloads. Raster size is limited to 16 million pixels; PNG output to 32 MiB. The injected encoder checks PNG MIME/signature and handles null/error, timeout, abort during header validation, and late/duplicate callbacks. `parseCaptureMetadata` rejects unknown nested fields and inconsistent held/scene timing, returning owned data.

`frame-artifact.ts` defines `.lucid-frame` version 1: a 20-byte header (eight bytes `LUCDFRM\0`, then big-endian uint32 version, metadata length, PNG length), at most 16 KiB of sorted-key canonical UTF-8 JSON, at most 32 MiB of PNG, and a 32-byte SHA-256 digest covering the entire preceding body. Exact lengths reject container truncation and trailing data. PNG validation checks signature, bounded chunk count, CRC32, ordering, IHDR pixel format/dimensions, and matching metadata raster limits; animated PNG chunks are rejected. BOM-prefixed and otherwise noncanonical metadata are rejected. The checksum establishes byte integrity only, with no authorship or model provenance guarantee.

Compressed PNG data passes through native `DecompressionStream('deflate')` using bounded input chunks. Validation consumes through EOF and checks the exact inflated scanline length and filter bytes for the pixel format and Adam7 passes, discarding output without retaining a full expanded image. This catches malformed data that the in-app browser's image decoder otherwise accepts as a blank image. The 16-million-pixel bound implies at most 144 million processed scanline bytes; abort cancels the reader. Unsupported browsers receive an explicit compatibility error. Imports must additionally pass browser image decoding and natural-dimension checks. Native codecs differ in their acceptance of extra data inside compressed streams; this is not a claim of canonical DEFLATE encoding or full pixel reconstruction. See the [Compression standard](https://compression.spec.whatwg.org/#supported-formats) and [PNG interlace specification](https://www.w3.org/TR/png-3/#8Interlace).

`ReviewFrameCapture` is mounted in all Stages. Its optional capture callback exists only in private proposal previews; capture also requires audience mode. File import and historical review remain usable in Design or renderer-error states. One shared abort controller and generation guard coordinate capture/import/export. Import uses a temporary decode URL with a ten-second timeout, then atomically replaces one retained Blob, metadata, PNG/JSON URLs, and optional prepared bundle URL. Failure preserves the preceding still; replacement/unmount release resources. Preparing a bundle produces a native download link, while separate PNG/JSON actions remain. No import changes Project, camera, playback, or proposal state. There is no provider image input, external upload, or durable gallery.

`transform_drones` applies one shared group operation while retaining each drone's individual geometry and unrelated channels. Translation is required; optional ENU scale and axis-angle rotation require an explicit pivot. The order is `pivot + R(scale × (position − pivot)) + translation`, with right-handed ENU rotation. Nonuniform, negative, and zero scales are supported. `base_and_keys` transforms each base and every position key, including dormant authored data. `key_at_time` transforms each evaluated scene-local target and merges only its position key; it does not transform the incoming blended viewport position. Timing, easing, and light channels are preserved. [Exact transform contract](AGENT_HARNESS.md#relative-movement-without-flattening-choreography).

Completed proposals support explicit local/file checkpoints through `checkpoint.ts` and `checkpoint-storage.ts`. Restore verifies project identity and canonical SHA-256 content (normalizing only the local revision), replays commands against the current revision, and reruns bounded review. It never commits or merges content. The separate local slot is capped at 1 MB UTF-8; portable files and base/draft snapshots at 32 MB, with shared command/expansion budgets. `impact.ts` compares authored documents without frame generation to report scene, channel, drone-record, and key changes. See [AGENT_HARNESS.md](AGENT_HARNESS.md#draft-recovery-and-measured-changes).

A separate [evaluation runner](AGENT_EVALUATIONS.md) exercises eleven synthetic editing requests through the actual tool loop. It checks full authored outcomes and preservation, independent of the model's wording or command strategy. Group-transform cases use independently constructed 90° geometric expectations, cover more than 128 irregular selected IDs plus dormant data, and distinguish scene targets from incoming blends. The audience-light and camera-light cases consume real comparison/inspection tool outputs before staging brightness keys, then measure again. The camera fixture maps elapsed 0/4/8 to show 1/2/3 seconds and checks analytically expected geometry [5,4,5], baseline lit counts [2,1,2], and final counts [4,3,4]. Independent checks cover captured poses/clocks, ordered before/after evidence, and full authored preservation including unrelated selected, unselected, and dormant work. Scripted fixtures use no live provider; live mode requires explicit case selection and provider configuration and remains unqualified.

`retime_cue` scales scene duration and optionally animation times and incoming blend; `transition_to_beats` resolves musical timing using project BPM. Transition easing runs through `frameAt` so viewport, picking, export, and review share the profile. See [TRANSITIONS.md](TRANSITIONS.md) for exact speed and boundary semantics. Proposed next layers include a versioned expression/modifier graph, sandboxed generator runtime, reusable groups, editable curve handles, and Blender/glTF import/export.

## Timing, review, and export

`AudioContext.currentTime` drives playback. Frame stalls do not accumulate a separate animation-clock drift. The original demo loops; imported tracks end naturally while the show continues. BPM is manual; it does not analyze or stretch audio. Import leaves media local to the browser session.

A cancelable worker handles reviews and CSV export. For static target formations it evaluates endpoint volume, analytic bounds on nonzero straight minimum-jerk transitions, and spatial-hash separation at intervals up to 0.5 s for fleets ≤2,000. Instant cuts are explicitly incomplete. For position-keyed motion, it samples the shared evaluator over the entire show; extrema/speed/acceleration are observations, not continuous bounds. Larger animated fleets get only sparse volume/motion samples and no separation review. Results never certify flight readiness.

The new editable bundle has `format: lucidity.design`, `formatVersion: 3`, and `engineVersion: 0.4.0`. Import accepts prior format-1 and format-2 bundles and bare Project v1 documents. Format 3 identifies the authored transition-profile semantics introduced in engine 0.4. Bundles retain coordinate/time conventions, source/keyframes, revision-matched review, and a `flightReady: false` boundary. Older consumers reject format 3 instead of silently treating authored transition profiles as the old default.

CSV exports ENU and RGB at 0.5 s intervals, including the exact endpoint, with a 350,000-row materialization limit. It is a preview artifact. The full JSON preserves fast light effects and interpolation semantics. Audio travels separately.

## Production continuation

Rendering 100,000 points, animating 100,000 authored channels, finding conflict-free assignments/paths, continuously validating them, and flying 100,000 aircraft are separate claims. Profile each against explicit hardware and show fixtures. Keep large planning/validation out of the UI thread, add deterministic compiled curves and content hashes, and partition fleet work as evidence warrants.

A future operator system should compile trajectories and lights, stage verified artifacts, synchronize scheduled execution, and monitor aircraft. Skybrush describes individual preloaded flight plans synchronized through a shared timebase; that is a relevant execution reference. [Skybrush operating overview](https://docs.skybrush.io/public/faq/latest/overview.html).

No aircraft transport, autopilot mission uploader, launch/landing planner, or operating authorization is implemented. See [VERIFICATION.md](VERIFICATION.md) for the distinction between executed checks and future qualification.
