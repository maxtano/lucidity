# One-drone mission evaluation — 2026-10-21

This is **ArduCopter 4.7.1 software-in-the-loop evidence**, not a live aircraft test or flight authorization. All MAVLink exchanges below used an isolated SITL process on `127.0.0.1:5760`; the scripts have no physical serial-port target. Lucidity's current implementation prepares and uploads a mission while disarmed and props-off, then reads it back. It does **not** arm, launch, monitor a live mission, or take over a physical aircraft.

## Reproduction

Official ArduPilot Copter-4.7.1 source was built in `/private/tmp/lucidity-ardupilot-sitl-471`. A clean simulator was started from `/private/tmp/lucidity-sitl-run-471` with official `copter.parm,copter-X.parm` defaults, `--model quad`, `--wipe`, and home `47.397742,8.545594,488,0`. No system-wide tools or parameters were changed.

From the drone-studio directory, with Node 23.3.0 and the local dependencies:

```sh
node --import tsx scripts/mission-sitl-service-smoke.ts --write
node --import tsx scripts/mission-sitl-launch-contract-eval.ts --execute-sitl-only
node --import tsx scripts/mission-sitl-guarded-eval.ts --execute-sitl-only --case=normal
node --import tsx scripts/mission-sitl-guarded-eval.ts --execute-sitl-only --case=land
node --import tsx scripts/mission-sitl-guarded-eval.ts --execute-sitl-only --case=takeover
node --import tsx scripts/mission-sitl-guarded-eval.ts --execute-sitl-only --case=missing-start-ack
node --import tsx scripts/mission-sitl-guarded-eval.ts --execute-sitl-only --case=link-loss
node --import tsx scripts/mission-sitl-guarded-eval.ts --execute-sitl-only --case=repeat
```

Start a **new `--wipe` SITL process for each guarded-eval command**; these are separate runs, not sequential commands against one aircraft state. The service script's default mode is read-only. `--write` is confined to localhost SITL, requires a disarmed ArduCopter and an empty or home-only mission, invokes Lucidity's `AircraftService` gates, stores a pre-upload backup in a temporary directory, and verifies a fresh full readback. The launch-contract script is an **independent simulator-only evaluation** of ArduPilot launch behavior. The earlier pilot-mode takeover was tested separately with `scripts/mission-sitl-flight-eval.ts --execute-sitl-only`. None of these scripts is wired to the product's Run Storyboard button.

## Observed mission storage

With a fresh GPS fix (`fixType=6`, `HDOP=1.21`) and global position, both initial `MISSION_COUNT=0` and initial home-only `MISSION_COUNT=1` paths passed. The final count-zero run compiled the saved **First live hover** template (2.0 m target, 5 s hold within a 15 s authored scene):

```text
initial-readback: count 0
service-upload: verified, count 4, pre-upload backup written
post-upload-readback: count 4, commands [16,22,19,21]
```

Those commands are ArduPilot home, `NAV_TAKEOFF` to 2.0 m, `NAV_LOITER_TIME` for 5 s at 2.0 m, and `NAV_LAND`. Exact readback comparison passed. The empty-mission backup contains `items: []`; home-only backup contains only seq 0. An earlier 2.5 m fixture also passed both count-zero and count-one storage paths; it was separate from the saved template. In a separate wire test, ArduPilot's legacy `MISSION_REQUEST` (ID 40) was observed during upload; Lucidity now accepts that request and replies with `MISSION_ITEM_INT` while retaining identity and mission-type checks. The first strict readback failure exposed Copter's canonical frame/parameter values; outbound items now use those exact values.

A later service-level simulator check called `verifyMissionForLaunch` after upload. It freshly downloaded all four stored items while disarmed and returned a 15-second, connection-generation- and storyboard-revision-bound **mission-storage proof** for the saved 2.0 m/5 s template. The first attempt refused to continue while SITL GPS fix was zero; after a fresh fix and position arrived, the readback passed. The service message explicitly says this does **not** authorize flight. Battery, RC, failsafe, EKF, home and pilot checks remain separate. No launch route, arming or mission-start command was added by this check.

## Observed simulator flight

Default Copter `AUTO_OPTIONS=0` blocked direct arming in AUTO. Arming normally in Stabilize and merely switching to AUTO did **not** take off; it auto-disarmed after about 10 s. Copter's `MAV_CMD_MISSION_START` after normal Stabilize arming did start the uploaded mission. No forced arming or pre-arm-check bypass was used.

```text
MISSION_CURRENT: 0 → 1 → 2 → 3 (then reset to 1)
MISSION_ITEM_REACHED: 1, 2
Mode: Stabilize → Auto
Relative altitude: 0 → peak 2.122 m → approximately 1.99 m hold → approximately 0 m
HEARTBEAT armed: true during flight, false after landing (about 18.6 s)
```

A second simulator run switched from AUTO to LOITER at about 1.215 m, then to LAND. The heartbeat again reported disarmed after landing. This tests a MAVLink mode-change analogue of pilot takeover, **not** the user's Zorro switch or RC path. The earlier 2.5 m fixture also flew and disarmed in SITL (peak 2.582 m, about 20.6 s), but the exact saved 2.0 m template is the main result above. Actual simulator duration differed from the authored 15 s scene because ArduPilot controls climb and descent timing.

## Repeat launch and telemetry loss in SITL

A later run used the same stored 2.0 m/5 s mission and queried simulator parameters before flight: `FS_GCS_ENABLE=0` (GCS failsafe disabled), `FS_THR_ENABLE=1` (RC throttle failsafe configured), `FS_OPTIONS=16`, and `FS_GCS_TIMEOUT=5`. These are **simulator readbacks**, not settings measured on the physical quad. After a first normal flight (MISSION_START `COMMAND_ACK=ACCEPTED`, peak 2.108 m, landed/disarmed), the test sent `MAV_CMD_DO_SET_MISSION_CURRENT` for seq 1 with reset flag 0 while disarmed. Copter returned `COMMAND_ACK=ACCEPTED`, emitted fresh `MISSION_CURRENT=1`, and stayed disarmed. Normal Stabilize arming plus another `MAV_CMD_MISSION_START` returned `ACCEPTED`; the repeated mission climbed to 2.125 m, passed through current items 1→2→3, then landed and reported disarmed.

On a third simulator start (`MISSION_START` ACK accepted), the localhost telemetry TCP socket was closed for 8.007 s while the quad was in AUTO, armed, at 1.007 m. On reconnection it reported a fresh AUTO/armed heartbeat at 1.842 m; subsequent telemetry showed the mission landing and disarming in AUTO. Progress during the outage was not observable: after reconnection, current item 3 was seen and item 1 reached was missed. This is **only a TCP telemetry loss observation under `FS_GCS_ENABLE=0`**. The test did not transmit periodic GCS heartbeats before disconnect, did not enable or trigger a GCS failsafe, and did not remove an RC link. It says nothing about the physical DroneBridge radios, Zorro, or the quad's configured GCS/RC failsafes. A launch monitor must treat an interrupted stream as uncertain and re-establish fresh mode, armed, mission-progress, position and landed state rather than infer completion from the earlier ACK.

## Deterministic checks and limits

The five `*.eval.test.ts` mission suites passed **43 tests**, and `tsc --noEmit` passed. They cover compiler eligibility, exact target filtering, unrelated/legacy messages, duplicate and out-of-order requests, bounded retries/deadlines, cancellation and USB loss, existing-mission refusal, empty-mission GPS gating, stale storyboard revisions, backups, readback mismatch, and middleware guards. These mocks are separate from the real SITL runs above. SITL's optional telemetry verification sometimes reported `failed` despite fresh GPS/position; its version-ACK timing should not be generalized to the physical DroneBridge link.

**Status of this initial evaluation:** A verified stored mission was not a safe one-click physical show; at this point the product had no physical launch entry point. A separate, injected SITL-only transaction implemented guarded reset/arm/start/observe/LAND behavior and passed one normal simulated flight (see below). The tested 2.0 m simulator trajectory did not validate a 1 ft hover, real altitude sensing near the ground, or the user's airframe. A guarded physical launch path and repeat-run handling were added later; see the current [launch gate](MISSION_LAUNCH_GATE.md).

## Guarded-transaction integration check (same date)

`scripts/mission-sitl-guarded-eval.ts` is a separate, explicit `--execute-sitl-only` harness for the new injected `SimulatorLaunchTransaction`. Its adapter is hardcoded to `127.0.0.1:5760` and has no physical serial-port destination. Each attempt started with a freshly wiped Copter 4.7.1 SITL instance. Attempts that passed readiness used a disarmed service upload and strict four-item readback, a fresh 15-second storage proof, synthetic SITL preflight evidence, and one ordered reset/ARM/START sequence. Some later EKF-gated attempts correctly stopped **before** upload. No forced arm, pre-arm bypass, or blind ARM/START retry was used.

The integration attempts exposed three important contracts. First, the reset command (`MAV_CMD_DO_SET_MISSION_CURRENT`, 224) returned a matched ACCEPTED ACK, but the controller correctly stopped as **unknown** when fresh `MISSION_CURRENT` reporting was not requested. Lucidity telemetry requests now include message 42. Second, fresh `MISSION_CURRENT` after reset reported `seq=1,total=3` even though `MISSION_COUNT`/readback contains four stored items. Copter 4.7.1's `GCS_MAVLink/GCS_Common.cpp` explicitly subtracts the home item from `MISSION_CURRENT.total`; the controller and pure progress observer now accept this verified Copter count while preserving the four-item readback requirement. Both early attempts sent only command 224 and never armed.

Freshly wiped SITL initially rejected normal non-forced ARM with `MAV_RESULT=4` and `Arm: Accels inconsistent`, then `Arm: Gyros inconsistent` on a separate run. In each case the controller stopped after exactly `[224,400]`; it sent no START. After 30 seconds of *pre-launch* simulator sensor warmup, reset and normal ARM both returned matched ACCEPTED ACKs (`1:1 → 254:190`), and the heartbeat reported armed/Stabilize. The subsequent `MAV_CMD_MISSION_START` (300) returned `MAV_RESULT=4` and STATUSTEXT `Mode change to Auto failed: requires position`; fresh `MISSION_CURRENT` remained `seq=1,total=3,state=2`, and the vehicle remained in Stabilize. The controller stopped **unknown** after exactly `[224,400,300]`, did not retry START, and the simulator-only harness requested disarm on the ground during cleanup. Copter's `mode.cpp` rejects AUTO when `position_ok()` is false; `system.cpp` shows that this depends on EKF position/failsafe state. A raw GPS fix of 6, HDOP 1.21 and streamed global position were **not** enough to prove AUTO position readiness. The normal guarded transaction therefore did **not** complete a flight in these runs; the earlier successful independent simulator flight above must not be mistaken for a pass of the new controller. At that point, LAND, takeover, and dropped-ACK cases had not yet run against SITL; the later gated results appear below. The controller's separate deterministic tests cover rejection/no-retry behavior, but those are injected fixtures, not simulator outcomes.

This showed that a live launch needs an explicit ArduPilot EKF/position-health gate, rather than relying on GPS and global-position messages alone. None of these runs checks the user's GPS, compass, RC takeover, radio failsafes, or airframe.

An EKF_STATUS_REPORT (MAVLink message 193) decoder and prelaunch gate were then added. The simulator-only harness requests a fresh report and requires horizontal absolute position plus altitude-estimate flags, while rejecting constant-position, uninitialized, and GPS-glitch flags. An initial post-gate run timed out before upload; its timeout did not yet print EKF flags. A diagnostic fresh-wipe run made the cause visible: **fresh flags 167 (0xA7), age 111 ms, GPS fix 6, disarmed/Stabilize, altitude 0.002 m**. The horizontal absolute-position bit 16 was absent and constant-position-mode bit 128 was set. The harness then moved its existing 30-second virtual-sensor warmup **before** the bounded 15-second EKF wait, without changing or bypassing the gate.

On the final fresh-wipe run, the EKF report showed **flags 831**, which satisfied the gate. Lucidity's service uploaded and read back the saved 2.0 m/5 s four-item mission while disarmed. The guarded transaction then sent exactly `[224,400,300]`: set current to seq 1, normal non-forced ARM in Stabilize, and `MAV_CMD_MISSION_START`. All three returned source/target-matched `COMMAND_ACK=ACCEPTED` from `1:1` to `254:190`. A fresh AUTO/armed heartbeat and `MISSION_CURRENT seq=1,total=3` established active mission start. Copter reported `Mission: 1 Takeoff`; the simulator subsequently reported disarmed, on ground (`EXTENDED_SYS_STATE.landedState=1`), and 0.016 m relative altitude. With `transaction.observe()` called periodically during flight and again at disarm, the controller ended **landed** with the reason “Mission progressed through LAND; fresh telemetry confirms disarmed and on ground.” The script exited 0. Its first successful run had observed only once after disarm and left the observer at `active`; that harness sampling error was corrected before this passing run. The final simulator process was stopped and TCP port 5760 had no listener.

Three more **independent fresh-wipe** Copter 4.7.1 runs exercised the same gate and saved mission through adverse simulator-only cases. Each began with fresh GPS fix 6, HDOP 1.21, firmware 4.7.1, battery 12.6 V, RC channels, on-ground state, and EKF flags **831** after the same 30-second pre-command warmup. Each uploaded and read back the exact four-item mission, then received matched ACCEPTED ACKs for reset (224), normal ARM (400), and START (300), with fresh AUTO/armed and `MISSION_CURRENT seq=1,total=3`. There was no forced arming, bypass, or blind command retry.

| Case | Observed simulator result | Command and recovery evidence |
| --- | --- | --- |
| Explicit LAND | During the climb, `transaction.land()` changed observer state **active → landing → landed**. Final mode LAND, disarmed, `landedState=1`, relative altitude **0.019 m**. | Transaction command trace exactly `[224,400,300,176]`; command 176 requested LAND. Harness exited 0. |
| Mode takeover | A simulator-injected `SET_MODE` to Loiter at **1.018 m** changed observer state **active → takeover**. The harness then sent a simulator-only LAND and observed disarm/on-ground at **0.018 m**. | Suppressed START ACK | The harness suppressed only command-300 ACK delivery to the transaction adapter. Each SITL process was stopped before the next fresh-wipe case; afterward TCP port 5760 had no listener. These cases validate the **injected loopback transaction**, not the app's physical Run control, the DroneBridge radios, or a Zorro RC switch. The takeover is a MAVLink mode-change analogue only. The suppressed ACK case is a deliberate adapter fault; it shows the controller stays uncertain even when the aircraft acts on a command, which is why a physical workflow must reconcile fresh telemetry rather than retry.

Further fresh-wipe runs examined telemetry loss and replay after landing. They passed the same 30-second warmup and EKF flags **831**, used the same strict four-item storage readback, and launched with accepted reset/normal ARM/START ACKs. No prearm bypass, forced arming, or blind START retry was used.

- **Midflight loopback outage passed its fail-closed contract.** The harness destroyed the `127.0.0.1:5760` TCP socket at **1.009 m** during AUTO. The progress reducer became `uncertain` and the transaction became **unknown**, with reason “Aircraft link was lost or its generation changed; do not resume automatically.” Its command trace remained `[224,400,300]`. After a **2.5-second** interruption, a new receive-only service connection and new aircraft identity saw the actual SITL vehicle still **AUTO/armed at 1.877 m**, `MISSION_CURRENT seq=2,total=3`, and `landedState=2`. The old transaction stayed unknown. A **separate simulator-only LAND** command then produced LAND/disarmed/on-ground at **0.006 m**; the transaction still did not claim autonomous completion. The first harness attempt had correctly refused an in-flight `requestTelemetry()` call (`AircraftServiceError 409: Telemetry requests require a disarmed aircraft`); the harness was corrected to inspect naturally streamed flight state, then request full telemetry only after disarm. The successful run exited 0.
- **Replay exposed and then resolved a terminal sequence race in SITL.** The first attempt used a new full mission readback/proof and fresh transaction after the first landing, and the second launch sent exactly `[224,400,300]`. The simulated vehicle landed/disarmed, but the observer failed closed as **unknown** because `MISSION_CURRENT` fell from seq 3 to 1 while the latest heartbeat still said armed. A later diagnostic trace caught seq 3 at timestamp **1792610781263**, on-ground state 1 and altitude **−0.027 m**, followed by seq 1 at **1792610781757** while the armed heartbeat was older; the next heartbeat reported disarmed. Copter 4.7.1 source explicitly disarms on `NAV_LAND` completion (`ArduCopter/mode_auto.cpp`) and resets the mission during disarm (`ArduCopter/AP_Arming_Copter.cpp`). Thus a new mission-current packet can precede the next disarmed heartbeat. The observer now **defers only that terminal seq 3→1 pattern** when it already saw airborne flight, prior LOITER completion, final LAND, fresh on-ground/near-zero position, and an older armed heartbeat. It never calls the run landed from the reset alone: a newer disarmed heartbeat must arrive within **3 seconds**, or it returns unknown. An airborne regression and a newer still-armed heartbeat remain fail-closed; deterministic observer/transaction suites passed **33/33** and TypeScript passed.
- **One final fresh-wipe replay retest passed.** The first transaction reached **landed** at **0.007 m**. While disarmed, the harness switched SITL to Stabilize, obtained a distinct fresh four-item readback proof and fresh preflight, and used a new transaction. Its reset advanced `MISSION_CURRENT` timestamp from **1792610952689** to **1792610954192**, and the second launch issued exactly `[224,400,300]` with fresh AUTO/armed seq 1. Both cycles observed **active → landed**; the second ended disarmed/on-ground at **0.008 m**. In both cycles, the trace showed seq 3→1 near ground while the last decoded heartbeat still said armed, followed by disarm; the observer waited for that disarmed evidence. The harness exited 0. This proves only an independent simulator replay on the same loopback session, not safe physical rerun or a user interface action.

The simulator was stopped after each run and TCP port 5760 had no listener. A loopback TCP outage is **not** a DroneBridge, radio, GCS-failsafe, or Zorro test. Reconnection evidence must not resume the original transaction automatically. EKF flags are a necessary preflight signal, not proof that Copter's internal `position_ok()` or the user's quad will pass. The physical Run control was disabled during these harness runs; it was subsequently implemented behind the pilot and aircraft checks in the current [launch gate](MISSION_LAUNCH_GATE.md).

## Physical command class through injected SITL adapter

After the guarded physical Run path was implemented, `scripts/mission-sitl-physical-eval.ts` connected its `PhysicalLaunchTransaction` to **only** `127.0.0.1:5760` through an injected TCP adapter. The path labelled `/dev/cu.usbmodemSITLONLY` is inert; this harness has no physical serial destination. Each scenario started a freshly wiped Copter 4.7.1 SITL and used the exact four-item mission with full upload/readback, virtual-sensor warmup, fresh EKF evidence, and normal non-forced arming. These results exercise the physical command class, not the real-aircraft HTTP preflight, DroneBridge, Zorro, or flight dynamics.

| Scenario | Simulator observation |
| --- | --- |
| Normal | Correlated reset/ARM/START commands `[224,400,300]`; AUTO/armed then landed, disarmed and on ground. |
| Explicit LAND | `[224,400,300,176]`; observed active → landing → landed, LAND mode and final disarm. |
| START ACK hidden | The vehicle entered AUTO but the transaction returned **unknown** and sent no retry; a separate simulator-only LAND recovered it. |
| Telemetry loss | During AUTO the transaction returned **unknown**. A new receive-only connection saw the aircraft still AUTO/armed; it did not resume or declare success. A separate simulator-only LAND ended the run. |
| Repeat | Two flights required separate fresh readback/proofs and resets. Both reached landed/disarmed/on-ground; peaks were about 2.14 m and 2.13 m. |

The UI and service preflight were separately exercised with injected fixtures. An actual full service-to-DroneBridge-to-aircraft mission has **not** been run. The physical quad still needs pilot AltHold/Loiter and reachable switch-takeover checks, a disarmed props-off mission transfer/readback, and field battery/GPS/compass/failsafe review before a supervised Lucidity launch.
